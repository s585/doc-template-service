# План реализации MVP генерации документа

Дата: 2026-04-02

## Назначение

Этот документ фиксирует практический план реализации MVP-сценария генерации документа по шаблону.
План опирается на уже реализованный CRUD шаблонов, текущую схему БД и существующие форматные процессоры.

## Текущее состояние

- CRUD шаблонов реализован.
- Импорт шаблона с парсингом placeholder-переменных реализован.
- В `template.processor` уже есть форматные обработчики для `DOCX` и `XLSX`.
- `TemplateProcessingFacade` пока умеет только `extractVariables(...)`.
- В БД уже созданы:
  - `t_generated_document`
  - `t_generated_file`
  - `t_generation_job`
  - `t_generation_job_attempt`
- Generation API и generation use cases пока не реализованы.
- Асинхронная обработка и worker-оркестрация пока не реализованы.
- Получение данных бизнес-объекта для вычисления значений переменных пока не реализовано.

## Цель MVP

Реализовать асинхронную генерацию документа по существующему шаблону с сохранением статуса запроса, внутренней очереди обработки и итогового файла в file-storage.

## Границы MVP

### Входит

- асинхронный запуск генерации;
- идемпотентность по `requestId`;
- чтение шаблона из file-storage;
- получение маппингов шаблона;
- вычисление значений переменных по данным бизнес-объекта;
- генерация одного итогового файла в формате исходного шаблона;
- сохранение результата в file-storage;
- обновление `generated_document`, `generated_file`, `generation_job`, `generation_job_attempt`;
- API получения статуса и результата генерации;
- базовые логи и минимальные метрики.

### Не входит

- синхронная генерация;
- конвертация между форматами;
- сложные шаблонные конструкции;
- распределенная очередь;
- отдельный микросервис generation;
- расширенные retry-политики и сложный scheduler;
- массовая генерация.

## Базовые допущения

- На MVP генерируется файл того же формата, что и шаблон.
- Один запрос генерации создает одну запись `generated_document`.
- Для одного `generated_document` в MVP создается один `generated_file`.
- `requestId` уникален в рамках `tenantId` и используется как ключ идемпотентности.
- Источник бизнес-объекта будет подключен отдельным adapter/use case, без смешивания с `template` CRUD.
- Реализация generation размещается в отдельных пакетах `generation.*`, а не внутри `template.*`, чтобы не мешать дальнейшей модульной декомпозиции.

## Целевая схема потока

1. Клиент вызывает `POST` на запуск генерации.
2. Сервис проверяет идемпотентность по `tenantId + requestId`.
3. Создаются записи в `t_generated_document`, `t_generated_file`, `t_generation_job`.
4. Фоновый worker забирает `generation_job` в обработку.
5. Worker читает шаблон и mappings.
6. Worker получает бизнес-объект и вычисляет значения переменных.
7. Форматный процессор подставляет значения и формирует итоговый файл.
8. Итоговый файл загружается в file-storage.
9. Обновляются статусы `generated_file` и `generation_job`.
10. Клиент получает статус и ссылку/идентификатор результата через read API.

## Этапы реализации

## Этап 1. Зафиксировать generation API-контракты

Нужно сделать:

- определить endpoint запуска генерации;
- определить endpoint получения статуса генерации;
- определить endpoint получения списка генераций для объекта или шаблона, если он нужен UI в MVP;
- зафиксировать DTO:
  - `GenerationCreateRq`
  - `GenerationRs`
  - `GeneratedDocumentRs`
  - `GeneratedFileRs`
- зафиксировать обязательные поля:
  - `templateId`
  - `entityId`
  - `objectId`
  - `requestId`
- определить коды ошибок и поведение идемпотентного повтора.

Результат:

- контракт generation API в `api`-модуле;
- понятный внешний сценарий для UI и интеграций.

## Этап 2. Зафиксировать доменную модель и статусы generation

Нужно сделать:

- ввести модели:
  - `GeneratedDocument`
  - `GeneratedFile`
  - `GenerationJob`
  - `GenerationJobAttempt`
- определить enum/статусы для:
  - generated document
  - generated file
  - generation job
  - generation job attempt
- описать допустимые переходы состояний;
- проверить соответствие статусов текущим колонкам БД;
- при необходимости добавить changelog на недостающие поля или индексы.

Результат:

- единая модель жизненного цикла генерации;
- отсутствие неоднозначности между read-model и очередью.

## Этап 3. Реализовать persistence-слой generation

Нужно сделать:

- репозитории для:
  - `generated_document`
  - `generated_file`
  - `generation_job`
  - `generation_job_attempt`
- методы:
  - create/findById/findByRequestId
  - updateStatus
  - createAttempt/finishAttempt
  - acquireNextJob
  - releaseLock
  - markCompleted
  - markFailed
- поддержку lease-lock через `locked_by` и `locked_until`;
- выборку заданий с ограничением параллелизма.

Результат:

- рабочий foundation для асинхронной обработки.

## Этап 4. Реализовать use case запуска генерации

Нужно сделать:

- controller -> web adapter -> use case для `POST /generation`;
- проверку существования шаблона и его доступности;
- проверку идемпотентности по `requestId`;
- создание read-model:
  - `generated_document`
  - `generated_file`
- создание записи `generation_job`;
- возврат ответа со статусом `ACCEPTED` либо согласованного текущим API кода.

Результат:

- пользователь может инициировать асинхронную генерацию без реального выполнения в HTTP-потоке.

## Этап 5. Реализовать worker и orchestration

Нужно сделать:

- компонент фоновой обработки job;
- периодический poller или другой простой механизм запуска;
- lease-lock для защиты от двойной обработки;
- запись `generation_job_attempt`;
- корректное завершение job в success/error;
- ограничение параллелизма через конфигурацию.

Результат:

- внутренняя очередь начинает реально обрабатываться;
- появляется контролируемый execution flow для MVP.

## Этап 6. Реализовать получение данных бизнес-объекта

Нужно сделать:

- ввести отдельный adapter/gateway получения данных объекта по `entityId` и `objectId`;
- определить внутренний формат данных, доступный expression/value resolver;
- обработать ошибки:
  - объект не найден
  - поле отсутствует
  - интеграция недоступна
- минимально покрыть таймауты и диагностические логи.

Результат:

- generation use case получает исходный data context для вычисления переменных.

## Этап 7. Реализовать вычисление значений переменных

Нужно сделать:

- пройтись по mappings шаблона;
- вычислить значения из `source`, `path`, `referenceValuePath`, `expression`;
- реализовать минимальный value resolver;
- определить правила работы с `null`, отсутствующими полями и обязательными значениями;
- отдельно поддержать `generated_file_name`.

Результат:

- на вход форматному процессору передается готовый map значений.

## Этап 8. Расширить форматные процессоры на генерацию файла

Нужно сделать:

- расширить `FormatAwareTemplateProcessor` методом генерации, например `generate(byte[] templateContent, Map<String, Object> values)`;
- реализовать подстановку значений для `DOCX`;
- реализовать подстановку значений для `XLSX` либо явно ограничить MVP одним форматом;
- сохранить текущую функциональность `extractVariables(...)`;
- унифицировать поведение при отсутствии значения и при ошибке подстановки.

Результат:

- появляется реальный технический механизм сборки итогового документа.

## Этап 9. Реализовать интеграцию с file-storage для generation

Нужно сделать:

- скачать файл шаблона по `s3Key`/идентификатору;
- загрузить итоговый файл;
- сохранить `s3_key`, `size_bytes`, `checksum`;
- определить naming strategy для выходного файла;
- обработать ошибки file-storage и обновление статусов.

Результат:

- итоговый документ физически сохраняется и доступен для скачивания.

## Этап 10. Реализовать read API результата

Нужно сделать:

- endpoint получения статуса генерации по `documentId` или `requestId`;
- DTO результата со статусом документа и файла;
- возврат информации об ошибке, если генерация завершилась неуспешно;
- при необходимости endpoint списка генераций по объекту.

Результат:

- UI может опрашивать статус и получать артефакт результата.

## Этап 11. Наблюдаемость и защита от регрессий

Нужно сделать:

- логи по ключевым шагам:
  - create request
  - acquire job
  - fetch object
  - evaluate mappings
  - generate file
  - upload result
- минимальные метрики по времени и ошибкам;
- unit-тесты на:
  - status transitions
  - value resolving
  - generation processors
  - orchestration state updates
- интеграционные тесты на happy path и error path.

Результат:

- MVP можно безопасно развивать дальше.

## Рекомендуемый порядок реализации

1. Этап 1: generation API-контракты.
2. Этап 2: доменная модель и статусы.
3. Этап 3: persistence generation.
4. Этап 4: запуск генерации без реального worker.
5. Этап 5: worker и lease-lock.
6. Этап 8: подстановка значений в шаблон.
7. Этап 9: file-storage для generation.
8. Этап 6: получение бизнес-объекта.
9. Этап 7: вычисление значений переменных.
10. Этап 10: read API результата.
11. Этап 11: наблюдаемость и тесты.

## Первый инкремент, который имеет смысл делать сразу

Первым рабочим инкрементом рекомендуется собрать вертикальный срез без сложной интеграции с бизнес-объектом:

1. Зафиксировать generation API.
2. Создать generation persistence.
3. Реализовать `POST /generation` с созданием `generated_document`, `generated_file`, `generation_job`.
4. Поднять простой локальный worker.
5. На время первого среза подставлять тестовые или constant-значения из mapping.
6. Довести сценарий до физической генерации одного файла и сохранения его в file-storage.

Такой срез быстро проверит:

- жизнеспособность схемы БД;
- корректность статусов;
- работу очереди;
- форматный механизм генерации;
- интеграцию с file-storage.

## Открытые решения перед стартом кодирования

- Подтвердить, поддерживаем ли в MVP оба формата (`DOCX`, `XLSX`) или начинаем только с `DOCX`.
- Подтвердить точный контракт получения бизнес-объекта.
- Подтвердить набор статусов для UI и внутренней очереди.
- Подтвердить, нужен ли отдельный endpoint списка сгенерированных документов в MVP.
- Подтвердить, какой HTTP-код возвращает запуск генерации: `200` или `202`.

## Что предлагается делать следующим шагом

Следующий практический шаг: реализовать Этап 1 и сразу зафиксировать generation API-контракт в `api`-модуле, после чего можно без потери темпа переходить к persistence и первому вертикальному срезу.
