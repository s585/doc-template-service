# Соглашения по реализации шаблонов

## Архитектурные слои
- `controller`: принимает HTTP-запросы и делегирует в `WebAdapter`.
- `adapter`: web-адаптеры и внешние адаптеры интеграций.
- `usecase`: оркестрирует обработку конкретного пользовательского сценария.
- `service`: работает с доменной моделью и инкапсулирует доменную бизнес-логику.
- `repository`: отвечает за доступ к БД и JSONB.
- `converter`: конвертация между DTO и внутренними моделями.

## Ответственность слоев
- `controller` не конвертирует DTO в модели и обратно.
- `TemplateWebAdapter` выполняет конвертацию `dto <-> model` и вызывает use case / service.
- `usecase` может вызывать сервисы, репозитории, feign-клиенты и форматные обработчики.
- `service` работает с моделью `Template` и связанными доменными сущностями.
- `repository` работает с внутренними моделями и `JSONB`.

## Доменные правила
- `template.code` уникален в рамках `tenantId`.
- Проверка уникальности `code` относится к доменной бизнес-логике и выполняется в `TemplateService` методом `checkCodeUnique(...)`.
- `Template` является агрегатом и может содержать `mappings`.
- При import для автосозданных mapping заполняется только `definition.scope`.
- При import `definition.type`, `definition.source`, `definition.expression` не заполняются автоматически.
- Если одна и та же переменная найдена с разными `scope`, import завершается ошибкой `400`.

## Работа с форматами файлов
- Низкоуровневая работа с файлами выносится в форматные обработчики.
- Общий контракт: `FormatAwareTemplateProcessor`.
- Реализации: `DocxTemplateProcessor`, `XlsxTemplateProcessor`.
- Форматные обработчики отвечают за извлечение переменных и определение `scope`.
- Для `scope = FILE_NAME` при import создается отдельный mapping с фиксированным ключом `generated_file_name`.
- Значение для `generated_file_name` по умолчанию берется из `TemplateCreationRq.name` через `CONSTANT` source.
- Для `DOCX`: текст/header/footer -> `VALUE`, таблицы -> `TABLE`.
- Для `XLSX`: на текущем этапе все найденные переменные считаются `TABLE`.

## Конвертация и библиотеки
- Для `DTO <-> model` используется `MapStruct`.
- Для всех `DTO` и моделей использование `Lombok` обязательно.
- Экспериментальный функционал Lombok не используется, кроме отдельно согласованных случаев.
- В `impl` используется `checker-qual`.
- По умолчанию значения считаются `non-null`.
- Аннотациями помечаются только места, где `null` допустим по контракту.
- Для сериализации `JSONB` используется `Jackson ObjectMapper` через helper в repository-слое.
- Для HTTP-интеграций используется `Spring Cloud OpenFeign`.
- Для работы с DOCX/XLSX используется `Apache POI`.
- Для SQL используется `jOOQ`.

## Коды ошибок
- Все используемые коды ошибок должны быть собраны в одном файле для последующего резолвинга.
- Текущее место хранения кодов ошибок: `CrmErrorCodes`.
- Сообщения для кодов ошибок должны храниться в `messages.properties` и резолвиться через `Spring MessageSource`.

## Настройки
- Префикс настроек приложения: `saas.doc-template`.
- Настройки filestorage URL задаются через `spring.cloud.openfeign.client.config.file-storage-client.url`.
- Настройки переменных шаблона: `saas.doc-template.template.variable.*`.
- Настройки file storage: `saas.doc-template.file-storage.*`.

## Применяемые подходы
- Идем от домена, а не от технических слоев.
- Интерфейсы вводятся для `service`, `repository`, `adapter`, `usecase`, где есть смысл подмены/расширения.
- Переиспользуемые технические helper/util-классы не должны лежать внутри пакета доменной сущности.
- Имена методов должны быть единообразными и отражать назначение.
- Методы получения, возвращающие `Optional`, начинаются с `find`.
